EMS Unified Database Schema

A table-first schema for unifying weather, inverter/converter, site-energy, meter, and generation-report exports.

Common contract: every curated measurement should resolve to site_id, optional asset_id/channel_id, event_time, metric_code, numeric or text value, unit, quality status, and source-file lineage.

How to retrieve data and manage calculated fields

The database should have separate layers. Users normally query the typed tables or serving views; engineers can query the canonical observation layer when they need a metric that has not yet received a typed view.

1. Raw / staging

Keep the original file shape, header names, file hash, parser version, and rejected rows. This layer is for replay and audit—not dashboard queries.

2. Canonical facts

Use canonical_observations for the stable contract: site, optional asset/channel, event time, metric, value, unit, quality, and lineage.

3. Serving layer

Expose typed tables and reporting views such as inverter_readings, daily generation, and performance summaries for APIs, dashboards, and MCP tools.

4. Persisted calculations

Store expensive or frequently requested results in derived_metric_values and materialized views. Recalculate affected windows after ingestion and return freshness.

Retrieval examples

These examples illustrate the intended API/query pattern. Replace the parameters with the requested site and time range.

-- A. Query a typed inverter time series
SELECT event_time, ac_power_kw, dc_power_kw, voltage_v, current_a
FROM inverter_readings
WHERE site_id = :site_id
  AND asset_id = :asset_id
  AND event_time >= :from_time
  AND event_time <  :to_time
ORDER BY event_time;

-- B. Query a metric that only exists in the canonical layer
SELECT o.event_time, o.value_numeric, o.unit_code, o.quality_code
FROM canonical_observations AS o
JOIN metric_dictionary AS m ON m.metric_code = o.metric_code
WHERE o.site_id = :site_id
  AND o.metric_code = 'irradiance_w_m2'
  AND o.event_time >= :from_time
  AND o.event_time <  :to_time
ORDER BY o.event_time;

-- C. Calculate a daily energy summary from interval energy
SELECT site_id,
       date_trunc('day', event_time) AS day,
       SUM(value_numeric) AS energy_kwh
FROM canonical_observations
WHERE metric_code = 'energy_kwh'
  AND site_id = :site_id
  AND event_time >= :from_time
  AND event_time <  :to_time
GROUP BY site_id, date_trunc('day', event_time)
ORDER BY day;

-- D. Retrieve a calculated metric through a serving view
SELECT site_id, period_start, period_end, value_numeric, formula_version
FROM derived_metric_values
WHERE metric_code = 'performance_ratio_pct'
  AND site_id = :site_id
ORDER BY period_start;
Practical rule: store raw measurements once, define calculated metrics once, and expose them through stable views or materialized views. Persist calculated results only when you need audit snapshots, fast repeated retrieval, or a formula that is expensive to recompute.

5. Minimal PostgreSQL contract

CREATE TABLE canonical_observations (
  observation_id  BIGSERIAL PRIMARY KEY,
  site_id         BIGINT NOT NULL REFERENCES sites(site_id),
  asset_id        BIGINT REFERENCES assets(asset_id),
  channel_id      BIGINT REFERENCES asset_channels(channel_id),
  event_time      TIMESTAMPTZ NOT NULL,
  metric_code     TEXT NOT NULL REFERENCES metric_dictionary(metric_code),
  value_numeric   NUMERIC,
  value_text      TEXT,
  unit_code       TEXT,
  quality_code    TEXT,
  source_file_id  BIGINT NOT NULL REFERENCES source_files(source_file_id),
  ingested_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX ix_observations_site_time
  ON canonical_observations(site_id, event_time);

CREATE INDEX ix_observations_asset_time
  ON canonical_observations(asset_id, event_time);
